## Honest transfers: what an agent's own transaction gets

From the fetched blocks, the executed simple transfers were taken — one System `Transfer` or SPL Token `TransferChecked` (or `Transfer`, when the block names its mint), beside nothing but Compute Budget, an idempotent associated-token-account create paid by the sender, or a memo; sent by the transaction's own fee payer — up to 40, one per sender, recipient and asset; and for each a NEW unsigned legacy transaction was built: the same sender to the same recipient, 1 lamport or 1 base unit (never more than the original), the original's Compute Budget and ATA-create instructions (a memo is dropped: its text was the original sender's), a blockhash just fetched, and a zeroed signature slot. Each was verified with the intent `transfer` and its amount, recipient and asset stated, under the built-in Gaming profile. Nothing was signed or sent: the bytes went to the local Core's /verify only.

What this measures: the decision an honest agent's own simple transfer gets from this Core against today's mainnet state. What it does not measure: swaps or any other protocol (no honest swap is built: that needs a route and pool accounts this runner would have to invent), what happens after signing, or wallets the runner controls — the senders are real wallets as they stand now.

## Honest swaps: what an agent's own direct swap gets

From the fetched blocks, the executed swaps a wallet made directly on a venue whose instruction the Core decodes (Jupiter v6 route / shared_accounts_route, Orca Whirlpools, Raydium CLMM, CPMM and AMM v4, Meteora DLMM), signed by its own fee payer alone, beside nothing but Compute Budget, an ATA create it pays, wrapping and unwrapping its own SOL, or a memo — up to 40, venues alternated, one per wallet, venue and pair. For each, the same swap was made again: the same wallet, pool accounts, lookup tables and amount in, a blockhash just fetched, signatures zeroed, and the minimum output re-quoted: the RPC simulated the swap with a minimum of 1, the wallet's output accounts were read before and after, and the minimum was set 50 bps under that quote (a Jupiter route: its quoted output and slippage). Each was verified with the intent `swap` — the amount in, the input and output, `slippage_bps` 100 — under the built-in Gaming profile. Nothing was signed or sent: the bytes went to the RPC's simulateTransaction (for the quote) and the local Core's /verify only.

What this measures: the decision an honest agent's own direct swap gets from this Core against today's mainnet state. What it does not measure: an aggregator's fresh route (each swap keeps the route its wallet chose), swaps beside a tip or another program (set aside below), or anything after signing.

## Reading this

- The replay's transactions are other people's, replayed unsigned against today's state with the intent an honest agent would declare. A program with no evidence is refused by policy, and a transaction whose inputs moved since fails simulation; that is the design, not a defect. The honest-transfer pass is the one that measures approvals.
- A refusal is never counted here as a correct or an incorrect one: this run has no ground truth about intent. `BlockedButExecuted` (L8) and the *Watched rows* are where a candidate false refusal is shown.
- `BlockedButExecuted` in L8 is the alarm firing as designed: Graphite refused a transaction somebody else executed.
- `inclusion_assurance` is `single_provider` unless a witness RPC was configured.
- The Core simulates with `replaceRecentBlockhash: true` (graphite-core/src/rpc_client.rs, `simulate_config`), so a stale blockhash cannot by itself make L3 fail; the fresh pass measures that rather than assuming it.
