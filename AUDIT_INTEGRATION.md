# Graphite Integration Layer Audit Report

**Date of Audit:** July 24, 2026  
**Auditor:** Superagent Integration Audit Specialist  
**Target Directory:** `/app/.cert/graphite/`  

---

## Executive Summary

An exhaustive analysis of the Graphite transaction verification project's integration layer, SDKs, HTTP server, and AI layer was performed. 

The results show a **stark contrast** between two halves of the system:
1. **The Core Verification Engine and SDKs are production-ready, high-quality, and robust.** The Rust Core is incredibly rich, the Go and TypeScript SDKs are clean, fully realized, and have real test suites.
2. **The Solana Agent Kit (SAK) integration and Python AI Layer are stubs/heuristics.** SAK is literally a skeleton adapter with *no dependency* on Solana Agent Kit itself and a commented-out demo. The Python AI Layer is a basic regex matcher posing as an NLP model.

Here is the breakdown of what is **REAL**, what is a **STUB**, and what **NEEDS TO BE BUILT** to achieve full production readiness.

---

## 1. Solana Agent Kit (SAK) Integration (`integrations/solana-agent-kit/`)

### Brutal Truth: **STUB / DRY-RUN ADAPTER**

* **Does it import real `solana-agent-kit` or type stubs?**
  * **No.** It does not import `solana-agent-kit` at all. In fact, `solana-agent-kit` is **not even listed** in the `dependencies` of `package.json`. The only dependencies are `@solana/web3.js` and `bs58`.
  * There are no type stubs either. It just implements local TypeScript interfaces representing the Graphite API.
* **Does it call real methods on real objects?**
  * **No.** The `GraphiteVerifiedAgent` class inside `src/index.ts` is an independent utility class that queries Graphite Core's `/verify` and the AI Layer's `/parse` endpoints via `fetch`. It has no binding or hook architecture for `SolanaAgentKit`.
* **Does it execute real transactions or just simulate?**
  * **Simulates/Prints only.** In `demo.ts`, the block of code that would instantiate a real `SolanaAgentKit` and execute an on-chain trade is **completely commented out**.
  * Running `tsx demo.ts --execute` simply prints a console warning:  
    `│  ⚠️  Live execution requires: npm install solana-agent-kit @solana-agent-kit/plugin-defi`
* **What would it take to make it actually run on devnet?**
  1. **Add SAK Dependencies:** Run `npm install solana-agent-kit @solana-agent-kit/plugin-defi` in the integration directory and add them to `package.json`.
  2. **Uncomment and Implement Live Execution Code:** In `demo.ts`, uncomment and implement the real `SolanaAgentKit` wallet setup using `bs58.decode(process.env.GRAPHITE_PRIVATE_KEY)` and the RPC connection.
  3. **Build Native SAK Hooks / Middleware:** Instead of a separate `GraphiteVerifiedAgent` wrapper where developer code must manually orchestrate `verify` and SAK execution, SAK should be wrapped natively. For example, a custom SAK action or tool, or a middleware plugin that intercepts all transactions generated by SAK actions and gates them through `verify` automatically.

## 2. TypeScript SDK (`sdk/typescript/`)

### Brutal Truth: **REAL & PRODUCTION-READY (LIGHTWEIGHT)**

* **Does it make real HTTP calls to the Rust server?**
  * **Yes.** `src/client.ts` uses standard `fetch` to send HTTP `POST` requests to `/verify` and `GET` requests to `/health` and `/manifests`.
* **Is the API surface complete or are methods stubbed?**
  * **Complete.** The SDK is fully typed (`src/types.ts`) and maps the complete Rust `VerificationInput` and `VerificationResult` schemas exactly. It supports Phase 1.5 advanced parameters such as `simulation_baseline` (with mean compute, standard deviation, and sample count) and decodes all details of the `resolved_accounts` and `transaction` structure.
* **Does it handle errors properly?**
  * **Yes.** It checks `!response.ok` and attempts to parse any error message returned from the Axum server before throwing a detailed JS `Error`.
  * *Note:* It does not include automatic retries, circuit breakers, or built-in client-side fail-closed fallbacks; error resilience must be handled at the application level.

## 3. Go SDK (`sdk/go/`)

### Brutal Truth: **REAL & PRODUCTION-GRADE**

* **Does it make real HTTP calls?**
  * **Yes.** It uses Go's standard `net/http` client with a configurable 30-second timeout to make real network requests to `/verify`, `/health`, and `/manifests`.
* **Is the API surface complete?**
  * **Complete.** All types match the Rust structs perfectly.
  * **High-Quality Detail:** It includes a custom `ByteArray` type with custom `MarshalJSON` and `UnmarshalJSON` implementations. This is crucial because Go default-serializes `[]byte` as base64-encoded strings, whereas Rust's `serde` expects a JSON array of integers (`[0, 1, 2, ...]`). This custom type bridges the serialization gap seamlessly.
* **Does it handle errors properly?**
  * **Yes.** It handles serialization errors, standard transport errors, and parses non-200 responses to surface the actual server error text.
* **Are there tests?**
  * **Yes.** `graphite_test.go` contains comprehensive unit tests verifying client configuration, custom `ByteArray` array serialization, and successful round-trip unmarshaling of full, nested `VerificationResult` objects.

## 4. HTTP Server (`graphite-core/src/server.rs`)

### Brutal Truth: **REAL CORE API (Lacks CORS & Production Resilience Middleware)**

* **Does the axum server actually work?**
  * **Yes.** It is a functional Axum server utilizing Tokio that compiles and runs correctly.
* **What endpoints does it expose?**
  * `POST /verify`: Full transaction verification pipeline.
  * `GET /health`: Server health check and package version.
  * `GET /manifests`: Returns a JSON array of all loaded protocol manifests.
* **Does it handle CORS, errors, timeouts?**
  * **Errors:** **Yes.** It maps Rust engine verification errors to `StatusCode::BAD_REQUEST` (400) and returns a clean, detailed JSON error payload.
  * **CORS:** **No.** There is **no CORS middleware** (e.g. `tower_http::cors::CorsLayer`) configured on the Axum Router. Web/dashboard clients calling this directly from a browser will fail due to CORS policies.
  * **Timeouts:** **No.** There are no built-in connection or request timeout filters on the Router (leaving it vulnerable to slowloris-type resource starvation).
* **Can it actually receive a transaction and return a verdict?**
  * **Yes.** It is fully integrated with the Rust verification pipeline. It takes a `VerificationInput` and feeds it through `GraphiteCore::verify()`, which performs account resolution, PDA derivation/verification, FakeSwap detection, CPI target validation, and policy checks. It then returns a true verdict (`approved: true` or `false`) with a complete analysis.

## 5. Python AI Layer (`python-ai-layer/`)

### Brutal Truth: **STUB (REGEX-BASED ADVISORY ONLY)**

* **Does it actually parse intent from natural language? Or just return a label?**
  * **It returns a structured label + params.** It parses a few strictly formatted English sentences into an advisory JSON schema containing parameters like `amount`, `input_token`, and `output_token`.
* **Is it a real NLP model or rule-based?**
  * **100% Rule-Based (Regex Heuristics).** There are **no** LLMs, transformers, neural networks, or machine learning libraries (such as spaCy or HuggingFace) used. It uses Python's standard `re` library with hardcoded regular expressions (`INTENT_PATTERNS`). If an agent phrase deviates from the hardcoded pattern (e.g., uses conversational filler or says "could you please swap..."), it fails to parse and falls back to `"intent_type": "unknown"`.
* **How does it communicate with the Rust core?**
  * **It does not communicate with the Rust core.** It runs as an independent HTTP server on port `8081`. The coordination is left entirely to the client-side integration layer (or the demo script), which calls the Python server `/parse` endpoint to extract suggested program IDs and discriminators, and then bundles that data into a request sent to the Rust core `/verify` endpoint.

## 6. CLI (`graphite-core/src/bin/graphite.rs` & `src/cli.rs`)

### Brutal Truth: **REAL, SOPHISTICATED & PRODUCTION-READY**

* **What commands does it support?**
  * `verify --file <path> | --stdin`: Runs the full Rust verification pipeline on a JSON input file or via stdin.
  * `manifests`: Lists all registered protocol manifests, showing program IDs and instruction counts.
  * `server --port <p>`: Launches the Axum HTTP verification server.
  * `benchmark`: Executes the verification performance benchmark suite.
* **Can it actually verify a transaction from the command line?**
  * **Yes.** It is 100% operational. It loads the manifest registry, parses the JSON payload, resolves accounts, checks PDA derivations, and outputs a complete, pretty-printed JSON `VerificationResult` to standard output.

## Action Plan for Production Readiness

1. **Fix the SAK Integration (Highest Priority):**
   * Implement a native plugin/hook architecture for Solana Agent Kit to automatically intercept all agent-initiated instructions and route them to `/verify`.
   * Add SAK to the dependencies and uncomment the demo's live execution code.
2. **Upgrade the AI Layer:**
   * Transition `intent_parser.py` from fragile regular expressions to a robust local NLP intent classification library or an LLM function-calling wrapper, to support true conversational natural language.
3. **Secure the Axum Server:**
   * Add CORS middleware to the Axum Router in `server.rs` to allow frontend dashboard integrations.
   * Add timeout and rate-limiting middlewares to protect the verification server under production loads.
